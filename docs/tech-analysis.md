# 动动乐园（dongdongpark.com）技术原理分析

> 分析日期：2026-11-10 · 分析对象版本：v0.55.1
> 用途：个人学习研究"浏览器摄像头体感游戏"的实现原理。本文只描述原理和架构，不包含对方的源码、素材或关卡设计。

## 0. 一句话结论

它**没有自研识别算法，也没有服务器参与识别**：用 Google 开源的 **MediaPipe Tasks Vision（WebAssembly）+ 官方 Pose Landmarker 模型**，在浏览器里把摄像头每一帧变成 33 个人体关键点；真正的功夫在关键点之后——**滤波、多人追踪、按躯干归一化的动作特征、带回滞的事件状态机**，再加一套统一的 Canvas 2D 小游戏框架。108 个游戏都是这套框架上的"插件"。

所以这类产品的门槛不在 AI，而在**信号处理的手感调校**和**游戏/体验设计**。

## 2. 产品形态

- 定位：用电脑摄像头玩的儿童体感游戏合集，3～18 岁，108 个游戏，每个学段三档难度。
- 两部分站点 **【实证】**：
  - **内容站**（首页、游戏介绍、指南、文章、体测标准）：构建时生成的静态 HTML，为 SEO 服务，几乎不带 JS。
  - **应用**（`/start`、`/games`、`/play/:gameId`、`/check`、`/leaderboard`）：单页应用，可安装成 PWA，横屏全屏。
- 流程：主菜单（一个人玩 / 两人比赛）→ 选学段和难度 → 选游戏 → 加载识别模型 → 站位引导 → 游戏 → 结算（举手隔空点"再玩一次"）。
- 另有设备检测向导 `/check`：浏览器 → 摄像头 → 光线 → 识别速度 → 站位 → 麦克风 → 声音，七步。
- 商业化：免费版每天限局数，会员不限；账号、排行榜、云相册走 `api.dongdongpark.com`。**这部分与识别技术无关，不在本文范围。**

## 4. 核心原理：从摄像头到游戏的六层流水线

```
┌──────────┐   ┌──────────────┐   ┌──────────────┐   ┌────────────┐   ┌──────────────┐   ┌────────┐
│ 1 采集   │ → │ 2 识别       │ → │ 3 追踪与滤波 │ → │ 4 身体模型 │ → │ 5 特征与事件 │ → │ 6 游戏 │
│ <video>  │   │ 33 个关键点  │   │ 镜像/稳定/   │   │ 手脚头的   │   │ 蹲/跳/挥/跑  │   │ 更新   │
│ 720p@30  │   │ ×N 个人      │   │ 谁是谁       │   │ 碰撞圆     │   │ 等连续量+事件│   │ + 绘制 │
└──────────┘   └──────────────┘   └──────────────┘   └────────────┘   └──────────────┘   └────────┘
   ~30 fps          ~15–30 fps（取决于机器）                                显示刷新率 60 fps
```

关键的一点：**识别频率和渲染频率是解耦的**。识别跟着摄像头的新帧走（最多 30 次/秒，慢机器更低），游戏按屏幕刷新率跑（60 次/秒），中间靠第 3 层的平滑把"一跳一跳"的关键点变成连续运动。

### 4.1 采集层

- `getUserMedia`，理想 1280×720 @ 30fps，前置摄像头；指定的设备找不到时自动退回默认设备。**【实证】**
- 视频接到一个不显示的 `<video>` 元素上，后面的识别和画面合成都从它取帧。
- 把浏览器的各种异常（没权限、没设备、被占用）翻译成给家长看的中文提示和修复办法。
- **看门狗**：定时检查 `video.currentTime` 有没有前进，几秒不动就判定画面卡死（摄像头被拔、休眠），提示重连。**【实证】**

### 4.2 识别层

- **加载**：先探测浏览器是否支持 WASM SIMD，选对应的运行时；WASM 和模型文件都用带进度的 `fetch` 自己下载，再以内存 buffer 交给 MediaPipe——所以界面能显示"6.4 / 22 MB"的下载进度。**【实证】**
- **推理后端**：先试 GPU delegate（WebGL），失败自动换 CPU。**【实证】**
- **配置**：`runningMode: 'VIDEO'`，`numPoses` 按模式设置，检测/存在/追踪置信度阈值 0.5。**【实证】** 追踪槽位比玩家数多 1 个，用来容忍画面里的旁观者。**【推断】**
- **默认模型** 是 `full`（WASM 13.5 MB + 模型 9.4 MB ≈ 界面显示的 22 MB）。**【推断】** 设备检测会按 `heavy → full → lite` 的顺序实测帧率，选第一个能达到约"摄像头帧率 × 0.7"的档位。**【实证】**
- **识别循环**：在主线程的 `requestAnimationFrame` 里跑；`video.currentTime` 没变就跳过（不重复识别同一帧）；传给 `detectForVideo` 的时间戳保证严格递增。**【实证】**
- **手和脸的省算力做法（很巧）**：不在整帧上跑手部/面部模型，而是**先用姿态关键点定位手腕和头部，把这些小区域裁出来拼到一张小图集（约 224～256 像素）上，再在图集上跑 Hand / Face Landmarker**，结果换算回原画面坐标。并且姿态识别和手/脸识别**错开在相邻两帧**执行，避免一帧里扎堆计算。**【实证】**
  - 手部 21 点 → 手势和伸出的手指数（数字、石头剪刀布类游戏）。
  - 面部 blendshapes → 张嘴、微笑、眨眼、鼓腮、头部朝向等表情量。

### 4.3 追踪与滤波层

- **镜像**：`x → 1 - x`，让屏幕像镜子；可见度取 `min(visibility, presence)`。**【实证】**
- **One Euro Filter（一欧元滤波器）**：对每个关键点坐标做自适应低通——动得慢时强力去抖，动得快时放开跟手，兼顾"稳"和"不拖"。这是体感交互里的标准做法。**【实证】**
- **多人关联**：每帧 MediaPipe 输出的人的顺序不固定，需要自己判断"这一帧的第 i 个人是上一帧的谁"。做法是按躯干中心的距离和包围盒重叠度做帧间匹配，给每个人一个稳定的追踪 ID。**【实证】**
- **双人模式分区**：屏幕左右各一半，玩家按所在区域归属到红队/蓝队。**【实证】**
- **渲染帧率上的二次跟随**：每个渲染帧让显示坐标按 `1 - exp(-dt × k)` 的比例追向最新识别结果，同时估算每个点的速度。这样识别只有十几帧时，画面里的小人依然是丝滑的。**【实证】**

### 4.4 身体模型层

把 33 个点整理成游戏好用的结构 **【实证】**：

- **碰撞圆**：头、左右手、左右脚、膝、肘，每个都有位置、速度、半径、是否可见。手的位置是从手腕沿"手腕→手掌"方向外推一点（关键点里的手腕并不在手掌中心）；半径按躯干长度缩放，站远站近手感一致。
- **躯干长度**（肩中点到髋中点）作为**全局尺子**：后面所有距离、速度都除以它，从而与人离摄像头多远无关。这是整套系统最重要的一个设计。
- 肩中点、髋中点、头部倾斜角等派生量。

### 4.5 动作特征与事件层

分两类输出：**连续量**（0～1 的强度，给游戏做模拟量控制）和**事件**（这一帧"发生了一次"）。

| 连续量 | 怎么算的（均按躯干长度归一化） |
|---|---|
| 活动量 energy | 主要关节速度的均值（去掉最快的几个抗抖），指数平滑。"木头人"类游戏用它判断动没动 |
| 原地跑 run | 膝/踝的竖直速度 |
| 侧倾 lean | 双肩连线的倾角 + 肩相对髋的横向偏移。当方向盘用 |
| 举臂 armLift | 肩高 − 腕高 |
| 下蹲 squat | 当前"髋到踝"的长度 ÷ 站直时标定的腿长 |
| 抬膝 kneeLift | 膝相对髋的高度，减去自适应基线 |
| 双脚间距、单脚站立时长、横移量、转头量、是否护胸 | 对应关键点的几何关系 |

| 事件 | 判定方式 |
|---|---|
| 蹲下 / 完成一次深蹲 | squat 的**回滞**状态机：超过高阈值记"下"，回落到低阈值以下才记"完成"，避免在阈值附近抖动重复触发 |
| 开合跳 | "脚开 + 手举" → "脚合 + 手落" 的两段状态机 |
| 高抬腿（左/右） | kneeLift 回滞 + 冷却时间 |
| 扇翅膀 | armLift 上下穿越两个阈值 |
| 出拳 | 手腕速度超阈值、方向背离肩膀、以水平为主，带冷却 |
| 踢腿 | 脚踝速度超阈值且明显高于另一只脚 |

**通用计数器（跳绳用）**【实证】：跟踪躯干中点的高度，维护一条慢速指数平滑的基线，观察"相对基线的偏移"的上下振荡；满足最小振幅、最大下沉、最长腾空时间、最小间隔时才 +1。带绳、不带绳都能数，因为它看的是身体的上下起伏而不是绳子。

**姿势匹配** 【实证：姿势库的数据形式】：目标姿势用"左右上臂角、左右前臂角、双腿张角、是否下蹲、是否抬膝"几个关节角来描述，同一份数据既用来画示意小人，也用来和玩家的关节角比对打分。

**标定**：开局时记录站位中心、站直腿长、膝盖基线，作为之后相对量的基准；基线还会缓慢自适应。

### 4.6 游戏层

- **插件式接口** 【实证】：每个游戏是一个独立模块，声明背景类型和配乐，提供 `create(ctx)`，返回 `update(frame)`、`draw(frame)`，以及可选的 `ai(playerIndex, frame)`。
- **框架提供给游戏的东西**：
  - `players[]`：每个玩家的碰撞圆、连续量、事件集合、所在分区、名字和颜色；
  - `stage`：画布、宽高、与分辨率无关的长度单位、文字绘制、粒子特效；
  - 计分、横幅、语音播报、音效、进度条、精彩时刻标记（供录像剪辑）；
  - 游戏时间、帧间隔、难度档位。
- **两种画面**：摄像头画面当背景再叠游戏元素（切东西、计数类）；或者纯虚拟场景里画一个跟着人动的卡通小人，摄像头缩成角落的小窗。**【实证 + 推断】**
- **电脑对手 / 演示模式**：`ai()` 直接产出"模拟的玩家输入"，单人玩时充当对手，没摄像头时还能驱动演示。**【实证】**
- **可复现的随机**：带种子的 xorshift 伪随机数——同一关发给好友，双方遇到的序列完全相同，才能公平比分。**【实证】**
- **节奏类**：一个 BPM 时钟（拍号↔时间互换）+ 三档判定窗口（完美/很好/还行）。**【实证】**
- **装扮**：帽子等贴图按头部碰撞圆的位置、大小、倾角绘制，所以会跟着头动。**【推断】**

### 4.7 案例：它的"穿墙洞"是怎么判定的

这是和我们要做的游戏最接近的一个，单独看了它的判定思路 **【实证】**：

- **画面**：2D，摄像头画面当背景，墙是画上去的。墙上的人形洞**一直跟着玩家走**——位置跟髋部中心、大小跟躯干长度（都带平滑），所以玩家站哪儿、离多远都不影响，洞只是"贴在人身上的一张示意图"。
- **判定只看关节角**，不做任何"身体在不在洞里"的几何计算：
  - 每条手臂取上臂朝向角和前臂朝向角（0° 朝下、90° 水平朝外、180° 朝上），与姿势模板的角度比，差值在容差内算对；上臂接近竖直举起时，前臂的误差打折（那时前臂角本来就不稳）。
  - 腿只在模板要求时才看：双腿张开看大腿平均张角够不够；下蹲、抬膝看"膝盖相对髋的高度 ÷ 躯干长"。
  - 所有误差都在容差内 → 过墙；同时算一个 0～1 的准确度用来计分。
- **难度只调三个量**：每面墙的时间（7.5 / 6 / 5 秒）、一局几面墙（8 / 10 / 12）、角度容差（40° / 32° / 25°），以及姿势池的大小（轻松只有五个纯手臂姿势，中等加入大字、叉腰等，困难加入下蹲和抬膝）。
- 没过也不扣命，只是少得分（面向小朋友的设计）。

**启示**：容差比直觉宽松得多——"困难"也有 25°，手臂伸直时相当于手腕可以偏出二十多厘米。这是按真实孩子的成绩调出来的，说明摄像头识别的抖动、延迟，加上人对自己姿势的控制精度，合起来需要这么大的余量。我们的游戏判定方式不同（真的做几何碰撞），但宽松程度以这组数为基准。

## 5. 体验层的几个技术点

| 功能 | 原理 |
|---|---|
| **设备检测 – 光线** | 把视频帧缩到很小，算亮度均值、对比度、中心与边缘的亮度差，判断"全黑（镜头盖）/ 太暗 / 过曝 / 逆光"【实证】 |
| **设备检测 – 站位** | 用关键点判断：没人 / 只看到一部分 / 头出画 / 太近 / 脚没进画面 / 太远 / 偏左偏右，给出"往后退一步"这类口语提示【实证】 |
| **举手隔空点按钮** | 举起的手映射为屏幕上的光点，在按钮上悬停一段时间即视为点击（dwell click）。孩子站在 2～3 米外不用跑回电脑前【来自作者描述，未核对实现】 |
| **语音带玩** | 本地神经网络 TTS 跑在 Worker 里，分"马上要读"和"预先准备"两个队列；引擎约 145 MB，首次下载后存 IndexedDB【实证】 |
| **录像** | 另开一张 960×540 的画布，每秒 24 帧把"摄像头画面 + 游戏画面"合成上去，`captureStream` 得到视频流，并入 Web Audio 的输出音轨，交给 `MediaRecorder`；优先 MP4，不支持则 WebM。数据只在内存里，用户点保存才落盘【实证】 |
| **防休眠 / 全屏** | Screen Wake Lock API、Fullscreen API；标签页切到后台时暂停【实证】 |
| **离线可玩** | Service Worker 预缓存全部应用代码；模型和 WASM 首次用到时缓存，URL 带内容哈希；应用页面"网络与缓存赛跑"，1.2 秒内网络没回来就先用缓存壳【实证】 |
| **国内下载加速** | 按时区判断是否在国内，WASM 优先走 npm 镜像，带"首字节超时/中途停滞"检测，失败回源站【实证，headless 日志里观察到了回源】 |

## 6. 性能设计要点

1. **算力全在客户端**，服务器只发静态文件——所以帖子火了服务器也没压力。
2. GPU 优先、CPU 兜底；SIMD 优先、非 SIMD 兜底；三档模型按实测帧率自动选。
3. 同一视频帧不重复识别；手/脸识别只在裁剪小图上做，且与姿态识别错帧。
4. 识别与渲染解耦，渲染侧插值补帧。
5. 游戏代码按需加载：进哪个游戏才下载哪个游戏的代码和贴图。
6. 渲染只用 Canvas 2D，贴图预先画好成精灵，低配电脑和教室一体机也跑得动。

## 7. 隐私设计

摄像头画面从不离开浏览器：识别在本地 WASM 里做，录像在内存里，页面没有第三方统计脚本。登录后同步的只有成绩和名单。这既是卖点，也是架构自然带来的结果（本来就不需要服务器看画面）。

## 8. 对我们自己实现的启示

1. **识别层直接用官方库和官方模型**，几十行代码就能拿到关键点，不是难点。
2. **值得花力气的是第 3～5 层**：一欧元滤波、多人关联、躯干归一化、回滞状态机——这几样决定了"跟不跟手、误不误判"。
3. **把"动作"抽象成框架提供的连续量和事件**，游戏只写玩法，不直接碰关键点；这是它能在短时间内堆出一百多个游戏的原因，也是扩展性的来源。
4. 语音、录像、离线、设备检测是"能给孩子和老师用"的工程化部分，可以按需逐步加。
5. 可以省掉的：本地神经 TTS（用浏览器自带语音合成起步即可）、账号/排行榜/支付等后端。

### 边界说明

本项目的目标是**学会并复现这套技术**，而不是复制这个产品。原作者明确表示暂不开源，并以此为生。因此我们的实现：

- **会做**：基于同样的公开技术（MediaPipe + Canvas）从零写一套自己的体感游戏框架和一组原创小游戏；
- **不会做**：照搬它的名称、品牌、美术素材、文案、具体关卡设计和界面外观，也不会把它的代码拷进本项目。

游戏玩法类型（碰触、躲避、计数、摆姿势等）是通用的，名字、素材和具体设计用我们自己的。
