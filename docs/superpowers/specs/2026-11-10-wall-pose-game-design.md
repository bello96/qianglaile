# 设计文档：体感框架 + 旗舰游戏「别撞墙！」

> 日期：2026-11-10 · 状态：已确认（用户答复见第 11 节，相关改动已并入正文）
> 前置阅读：`docs/tech-analysis.md`（对动动乐园的技术原理分析，本设计的六层流水线来自那里）
> 约定：标「**你说的**」的是用户明确提出的；标「**我的决定**」的是我替你做的选择，可以推翻。

## 1. 要做什么，为什么

**你说的**：看到动动乐园后想学会"浏览器 + 摄像头本地实时识别人体"这套技术，并且以后能往里加自己的游戏创意。最想先做出来的是一个"墙来了"式的游戏：人站在游戏区，前方一堵带人形挖孔的墙慢慢靠近，要在墙到身边之前摆好姿势穿过去；姿势不对被墙撞到，就掉进水里。参考图是一个 3D 场景：小人站在水池上的平台上，远处的墙上有人形洞。

所以这个项目是两样东西：

1. **一套自己写的体感框架**——把分析文档里的六层流水线（采集 → 识别 → 追踪滤波 → 身体模型 → 动作特征 → 游戏）每一层都实打实写出来，代码要能当教材读。
2. **一个做到好玩的旗舰游戏**——穿墙摆姿势，3D，能反复玩。

成功的样子：你打开网页、站到摄像头前，屏幕里的小人跟着你动；墙过来，你摆对了就穿过去、彩带飞起，摆错了被撞进水里。之后你想加一面新的墙，只需要摆个姿势按一下"存成新墙"；想加一个新游戏，照着示例游戏写一个文件。

## 2. 目标、非目标、反目标

### 目标（第一版）

- 旗舰游戏「别撞墙！」完整可玩：加载 → 站位标定 → 闯关 → 结算 → 再来一次。
- 体感框架分层清晰，游戏通过统一接口读"玩家状态"，不直接碰识别库。
- 扩展性落到实处：
  - **姿势实验室**页面：实时看骨架、关节角、动作特征；把当前姿势一键存成一面新墙；浏览全部墙的图鉴；录制/回放一段动作数据。
  - 一个约 150 行的**示例小游戏**（用手戳泡泡，摄像头画面当背景的 2D 玩法），证明"加一个游戏只要写一个文件"。
- 站在 2～3 米外也能操作：**举手悬停**就能点"开始""再来一次"。
- 没有摄像头、没有人也能跑：**模拟玩家**（演示模式）驱动整条流水线，用于自动化测试和首页演示。
- 全部在本机计算，摄像头画面不离开浏览器。

### 非目标（第一版不做，留好接口）

- 账号、排行榜、支付、云存储等任何后端。
- 双人同屏、手势（手指）识别、表情识别。
- 游戏录像与分享、PWA 离线安装、七步式设备检测向导、本地神经网络语音。
- 手机竖屏的专门适配（能打开，但不调优）。
- 大量小游戏。先把一个做好。

### 反目标（做成这样就算失败）

- **看起来像在抄**：名字、美术、文案、界面不照搬动动乐园，也不照搬电视节目《墙来了》或参考图里那款游戏。玩法类型相同，呈现是自己的。具体要避开的：
  - 动动乐园：站酷快乐体和 Nunito 字体；天蓝渐变背景 + 奶油色圆角卡片（底边带一道粉褐色厚边）+ 糖果色积木标题字的整体观感；它的红黄绿蓝紫配色组合（`#ff6b6b` `#ffd93d` `#6bcb77` `#4d96ff` `#b983ff`）；它的游戏名、文案、图标、贴图、音效设计。
  - 电视节目：蓝色泡沫墙配红色背景的演播室布景、节目名和口号。
  - 参考图里的游戏：暗青色低多边形场景、米色薄墙、木头人偶、四面围起来的水池。
- **判定和画面对不上**：看着明明进洞了却判撞墙，或者判过了却穿模。几何洞的判定和画出来的墙用同一份数据；人形洞靠"过关吸附 + 红色肢体提示"保证看到的和判的一致。
- 加新游戏、新墙要去改识别层的代码。
- 必须有真人站在摄像头前才能跑测试。
- 任何把摄像头画面发到网络上的行为。

## 3. 约束

- 运行环境：桌面 Chrome / Edge，普通笔记本摄像头（720p），集成显卡。识别目标 ≥ 24 次/秒（不够就自动降到轻量模型）。渲染 60 帧是**目标，不是硬约束**；硬约束是判定正确、操作跟手。
- **摄像头视野是个现实限制**：普通笔记本摄像头竖直视角只有 35～43° 左右，人站在 2 米处往往装不下全身，举手过头更容易出画。游戏不能假设"全身 + 举手"都看得见，必须按实际看得到的范围出墙（见 4.2 第 6 条）。
- 以本机 `npm run dev` 运行为主；`npm run build` 要能产出可直接托管的静态站点，但第一版不做部署配置。摄像头只能在 `localhost` 或 HTTPS 下使用。
- 识别库和模型文件放在项目里自托管，运行时不依赖任何外部 CDN。
- 本机网络现状（已实测）：npm 官方源连不上，npmmirror 直连可用；Google 的模型下载地址经代理可用。安装脚本要兼容这一点。
- 我无法真人实测。手感类的参数（容差、速度）只能先按模拟数据调，**最终需要你站到摄像头前试玩后再调一轮**。所有可调参数集中在一处。
- 项目目录目前不是 git 仓库；除非你要求，我不会 `git init` 或提交。

## 4. 游戏设计：「别撞墙！」

### 4.1 一局怎么玩

```
加载模型 → 站位引导与标定 → 3-2-1 → ┌─ 墙驶来（3.5～7.5 秒）─ 到达时判定 ─┐ → 没命了 → 结算
                                     └─ 下一面墙 ……本关的墙过完 → 升一关（更快更难）─┘
```

- **单人，每面墙一个洞（你说的）**。洞的造型两类都有：**人形洞**（摆出对应姿势）和**几何洞**（矮门要蹲、窄缝要收紧、斜窗要侧倾、偏门要挪一步、圆洞要缩成一团……），只要整个人钻得进去就行。
- **按关卡升级（你说的）**。一关若干面墙，过完升一关；关卡决定这一关出哪些造型、墙多快、洞口余量多大。大致节奏：
  - 第 1 关：只动手的对称人形，墙慢，洞跟着你站的位置开
  - 第 2 关：不对称的手臂姿势
  - 第 3 关：加入几何洞和双脚分开的姿势
  - 第 4 关：侧弯、下蹲、洞开在旁边需要挪步
  - 第 5 关起：单脚、弓步，洞口收紧，墙越来越快，没有上限

- **视角（我的决定）**：从小人背后看过去，墙从远处朝小人（也朝屏幕）驶来。这个视角下你举右手、小人的右手也在屏幕右边，方向和照镜子一致；而且墙是"从屏幕里朝你撞过来"，和你面对摄像头的真实感受吻合。
- **屏幕上的你（我的决定）**：一个跟着你动的 3D 小人，不是真人画面。左下角有摄像头小窗（可叠加骨架、可关闭），方便确认自己在不在画面里。
- **落位轮廓**：墙还在远处时，小人所在的位置就有一圈发光的轮廓，表示"墙到的时候洞会在这儿"。你可以提前对好。轻松和标准难度显示，挑战难度不显示。
- **实时反馈**：小人身上摆对的肢体是正常色，没摆对（或会撞墙）的肢体变红；屏幕上有"契合度"百分比和倒计时。
- **墙到的那一刻判定**（取最后约 0.25 秒内若干帧的多数结果，防止单帧抖动）。规则就是你说的那句——**姿势不对就被墙撞进水里**：

  | 结果 | 人形洞的条件 | 几何洞的条件 | 发生什么 |
  |---|---|---|---|
  | 撞墙 | 有肢体的朝向超出角度容差，或人不在洞的位置上 | 有身体部位明显陷进墙体 | 小人被墙撞下平台、落水、溅起水花；扣一条命 |
  | 过关 ★ / ★★ | 各段肢体都在容差内 | 整个人在洞里 | 墙从身上穿过去，得分，彩带 |
  | 完美 ★★★ | 而且很贴合 | 而且全程没蹭到边 | 高分，墙碎成彩块 |

- **过关时的"吸附"（我的决定）**：判定有容差，所以"判你过了"的时候手臂可能比洞口歪出去一点。为了不出现"明明过了却看着穿模"，墙到达前的最后一瞬，如果你的姿势在容差内，小人会被轻轻吸到洞的正中姿势上，干净利落地穿过去；没摆对则不吸附，红色的肢体就是撞墙的地方。这样画面和判定始终对得上。
- **命与进度（我的决定）**：三条命（图标用救生圈），关卡无上限，命用完结算；结算显示闯到第几关、过了多少面墙、得分。设置里有三档难度：轻松 / 标准 / 挑战（决定角度容差和墙速，挑战档不显示落位轮廓），默认标准，开局不强制选择。
- **同一关可复现**：墙的出场顺序由带种子的随机数决定，同一个种子遇到的墙完全一样（以后做"每日挑战""好友比分"的基础）。

### 4.2 墙洞是怎么来的（核心算法）

1. **姿势用关节角描述**。一份姿势数据 = 左右上臂、前臂、大腿、小腿在正面的朝向角，加上脊柱倾角、每段肢体的"缩短比例"（肢体朝向镜头时在正面看会变短，深蹲靠它表达）、可选的左右平移。约 22～24 个原创姿势，分四层难度：
   - 一层：只动手，左右对称（T 字、举高、大字、叉腰……）
   - 二层：左右不对称、双脚分开
   - 三层：侧弯、下蹲、整个人往旁边挪一步
   - 四层：单脚站、侧踢、弓步
   - 左右不对称的姿势自动有镜像版；可叠加左右平移。
2. **洞是按你的身材量身挖的**。标定时量出你各段肢体的长度；把目标姿势的关节角套到**你自己的肢体长度**上，算出"你摆这个姿势时身体在哪"，再往外放一圈余量，就是洞。所以大人、小孩、长臂短臂都一定穿得过。
3. **墙是一张网格上的"标量场"**。人形洞 = 到目标骨架各段（胶囊体）的距离小于"肢体半径 + 余量"的区域；几何洞 = 由圆、矩形、圆角条等基本形状拼出来的区域，尺寸同样按你的身材算（比如窄缝宽 = 你的肩宽 + 余量，矮门高 = 你站高的六成）。两类洞最后都是同一种数据。在一张约 2.5 厘米一格的网格上算出这个场，然后：
   - 做一次连通性修正：墙体必须和墙的上边或左右边相连。于是两腿之间、手叉腰围出来的三角这些"悬空的碎片"自动算作洞（现实里它们也会掉下来）。
   - 用等值线提取（marching squares）得到洞的轮廓 → 拉伸成有厚度的 3D 墙。
   - **几何洞的判定也查同一张网格**：玩家身体各段（胶囊体）取采样点，查它是否落在墙体里、陷进去多深；陷得不深（泡沫有弹性）不算撞。画面和判定用的是同一份数据。
4. **人形洞按关节角判定（参考原站的做法）**。比较玩家和目标姿势各段肢体的**朝向角**（上臂、前臂、大腿、小腿、脊柱）；朝向镜头而缩短的肢体（深蹲的大腿、抬起的膝盖）改比"缩短比例"。再加一条位置要求：人要站在洞的左右位置上。
   - 各段都在容差内 → 过关；按平均误差给 ★ 到 ★★★，并显示成"契合度"。
   - 有一段超出容差，或站位偏了 → 撞墙。超出的那几段就是小人身上变红的部位，结算横幅会说"左手没摆对"这类具体原因。
5. **半身模式（我的决定）**：如果标定时摄像头看不到腿（坐在桌前），这一局就是半身模式——只出上半身姿势，腿不参与判定，小人的腿用默认站姿。这样坐在电脑前也能直接试。半身模式和全身模式同等重要，姿势库里至少要有 10 个上半身能完成的姿势。
6. **按看得见的范围出墙（我的决定）**。标定时除了量身材，还量出"摄像头在你站的位置能看到多大一块"（用同一个坐标换算，把画面的上下左右边换成以你为中心的米数）。关卡生成器只从"目标姿势的每个关节都落在可见范围内"的造型里抽——比如摄像头只看得到 1.9 米高，就不会出要把手举到 2 米的墙。
   - 全身 / 半身在标定时确定，一局之内不变。中途如果站位明显变了（比如走近导致脚出画），提示"退回原位"，而不是悄悄换模式。
   - 可复现性的准确说法：**同一个种子 + 同一难度 + 同一模式和可见范围 + 同一造型池**，遇到的墙完全一样。
   - 标定时如果全身装不下，先提示"往后退一点 / 把屏幕往后仰一点"，实在不行再按能看到的范围开局，不强制。
7. **看不见的部位怎么判（我的决定）**。
   - 判定瞬间可见度很低的肢体：不参与判定（看不清不能冤枉人）。因为出墙时已经保证目标姿势在可见范围内，摆对的人不会遇到这种情况。
   - 头和双肩是底线：这几个点都看不见，说明人不在画面里——墙驶来途中持续 1 秒看不到人就**自动暂停**，回来 0.5 秒后继续；不会因为人走开而扣命。
8. **容差参考原站的实测值（你说的：参考上个游戏的做法）**。动动乐园的"穿墙洞"是纯关节角比对，容差按难度是 40° / 32° / 25°，这组数是它按真实孩子的成绩调出来的，比我最初设想的宽松得多。所以：
   - 人形洞的角度容差直接用这组数：轻松 40°、标准 32°、挑战 25°；随关卡升高再逐步收紧，但不低于下一档的值。
   - 洞口看得见的余量只负责"让洞看起来是个合身的人形"，不再承担判定；判定由角度容差决定，两者之间的视觉落差由过关时的"吸附"抹平。
   - 几何洞本身就开得宽松（比如矮门高度是站高的六成），再加几厘米"泡沫弹性"。
   - 低关卡的洞**开在你当时站的位置**（墙出现的那一刻取你的左右位置），不要求挪步；原站的洞是一直跟着人走的，我们只在出墙瞬间对齐一次，之后洞就固定了。从第 4 关起才有需要挪步的偏置洞。

### 4.3 画面与声音

- **美术方向（我的决定）**：晴天海面上的浮台闯关——明亮的天空、卡通水面、彩色泡沫板做的厚墙、圆润的玩具感小人（背后有号码布，因为我们总看他的背）。全部用代码生成的几何体和着色器，**不用任何外部美术素材**。与参考图那种暗色调低多边形木头人、围起来的水池明显不同。
- **小人**：用胶囊体和球体按关节位置逐帧摆出来（上臂、前臂、大腿、小腿、躯干、头、手、脚），不需要骨骼绑定。几何洞的判定用的身体轮廓就是这些胶囊体的正面投影。
- **反馈**：过关时墙碎成彩块和彩带；撞墙时闷响、小人被推下平台、水花、镜头轻微震动；连击有递进的音效。
- **声音**：全部用 Web Audio 实时合成（驶来的风声、倒计时、叮、扑通、水花、连击音阶），不带音频文件。姿势名用浏览器自带的中文语音播报，可关。
- **界面字体**：正文用系统中文字体；标题用一款自托管的开源中文展示字体（不选原站用的那款）。具体哪款留给实现时定。

## 5. 体感框架设计

### 5.1 分层与目录

```
src/
  engine/            与界面框架无关的纯 TypeScript
    camera/          打开摄像头、错误翻译、卡死看门狗
    vision/          下载并加载识别库和模型（带进度）、GPU→CPU 回退、识别循环
    tracking/        一欧元滤波、选定并跟住"玩家"这个人
    body/            关键点索引、身体模型（米制骨架、部位碰撞体、肢体长度标定）
    motion/          连续特征、带回滞的事件、通用起伏计数器
    input/           三种姿态来源，接口相同：摄像头 / 模拟玩家 / 录制回放
    audio/           合成音效、语音播报
```

### 5.2 几个关键的技术决定（我的决定）

1. **把图像坐标换算成"米"**。MediaPipe 同时输出图像关键点（准，但随人离镜头远近缩放）和世界关键点（以髋为原点、单位是米、与远近无关，但四肢末端不如图像关键点准）。每帧在两组点的正面投影之间拟合一个"缩放 + 平移"，用它把**图像关键点**换算进米制空间：正面位置取图像关键点的精度，尺度取世界关键点的稳定，深度只用于让 3D 小人看起来立体。这样站远站近、高矮胖瘦，进到游戏里都是同一把尺子。
   **已用真实数据验证**（官方 full 模型 + 一张真人全身照片，无头 Chrome 里实跑）：世界坐标以髋中心为原点，x 与图像同向、y 向下为正、z 朝镜头为负，躯干长约 0.50 米；图像关键点经这个拟合换算后，与世界关键点的正面投影平均只差 2.2 厘米、最大 3.3 厘米。所以这个方案成立。
2. **脚踩地**：小人的高度由"最低的那只脚贴地"决定，所以下蹲自然变矮，不需要额外标定地面。左右位置由髋中心相对标定位置的偏移决定。
3. **识别与渲染解耦**：识别跟摄像头新帧走（优先用 `requestVideoFrameCallback`），渲染按屏幕刷新率；渲染侧对关节位置做指数跟随补帧。
   - 第一版识别放在**主线程**（和原站一样，结构最简单、最好读）。代价是集成显卡上识别那一帧可能超出 16.7 毫秒，画面偶尔掉到 30 帧。
   - 识别层藏在统一的"姿态来源"接口后面。识别层做好后在本机实测单次识别耗时：**中位数超过约 8 毫秒，就把识别挪进 Web Worker**（传帧用 `createImageBitmap`），游戏代码不用改；没超过就不做。
4. **只跟一个人**：画面里有多个人时，选最靠中间、最大的那个作为玩家，之后按帧间位置连续性一直跟住他，旁人走过不会抢走控制权。
5. **模型档位**：默认标准模型（full）；启动时测几秒帧率，不够就换轻量模型（lite）。设置里可手动选。
6. **游戏接口**：每个游戏导出 `create(ctx)`，返回 `update(frame)` 和 `dispose()`，自己决定用 2D 画布还是 3D 场景。`ctx` 提供玩家状态（米制关节、图像关节、部位碰撞体、连续特征、事件、身材标定）、音效、语音、计分和横幅提示、随机数、难度。

### 5.3 自定义的墙存在哪（我的决定）

- 在姿势实验室摆好姿势点"存成新墙"时：
  - 用 `npm run dev` 运行时，开发服务器提供一个只在开发模式存在的写盘接口，把姿势追加到项目里的 `public/custom-poses.json`。这样新墙是**项目里的一个文件**，换浏览器也在，能进版本管理。
  - 作为静态站点运行时（没有写盘接口），存进浏览器本地存储。
  - 两种情况下都能导出 / 导入 JSON 文件，也能"复制成代码"贴进内置姿势库。
- 每面自定义墙有一个"加入闯关"开关，默认打开；难度层按姿势自动估（只动手 → 一二层，动腿或侧倾 → 三层，单脚 → 四层），可在实验室里手动改。
- 自定义墙进入随机池后，同一种子的出墙顺序会跟着变，这是预期行为。以后做"每日挑战 / 好友比分"时只用内置姿势池。

### 5.4 第一版实现的动作特征

连续量：活动量、侧倾、左右举臂、下蹲、双脚间距、左右抬膝。事件：跳、蹲下 / 起身（一次深蹲）、举手（供悬停光标用）。旗舰游戏主要用米制关节做几何判定；这些特征主要服务于姿势实验室的可视化、示例小游戏和以后的新游戏。新增特征照同一个模式加。

## 7. 怎么验证它是对的

1. **单元测试**（纯逻辑，不需要浏览器）：几何与标量场、一欧元滤波、坐标换算拟合、正向运动学、轮廓提取、判定（目标姿势本身 → 完美；轻微偏差 → 过关；错误姿势 → 撞墙；缩手站立 → 蒙混过关）、关卡生成的可复现性、特征与事件。
2. **模拟玩家跑完整局**：模拟玩家带噪声地摆对每面墙 → 应连续过关；故意摆错 → 应扣命直到结算。验证状态机、计分、难度递进。
3. **真实模型的端到端检查**：Headless Chrome + 一张真人全身照片做成的假摄像头视频 → 模型能加载、能出关键点、小人能出现、截图人工看一眼。这条链路已经在草稿环境里跑通过（照片 → 720p 基线 JPEG → MJPEG 假摄像头 → 无头 Chrome 里 GPU 模式识别成功；注意 Chrome 的假摄像头不认渐进式 JPEG，要先转成基线格式）。
4. **真人动作数据回放（可选，不依赖你）**：录制功能照做（见第 8 节第 3 步），录下来的只是关键点数字、不含画面，可以存成测试夹具（`tests/fixtures/recordings/`）。你说了不想中途录动作，所以开发过程**不依赖**它：容差按原站的实测值起步，用模拟噪声和公开照片验证。以后你或别人想录一段来精调，功能是现成的。
5. **你的真人试玩**：手感、速度的最后一轮调整依赖它。

测试用的真人照片用 MediaPipe 官方公开的测试图，由资源下载脚本拉到本地，**不提交进项目**。
